## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## App structure

Bottom tab navigator (`src/app/(tabs)/_layout.tsx`) with five tabs, in order: **Health Tips · Dashboard · Home · Settings · Account**. **Home** (`index.tsx`) is the opening tab — it is declared with `initialRouteName="index"` and sits in the middle position. Its icon and label are drawn a size up from the other four (`tabBarIcon` gets `size + 5` with a heavier `tabBarLabelStyle`), so the opening tab reads as the current one at a glance.

- **Health Tips** — `health-tips.tsx`: a featured "tip of the day" (rotates by calendar date) plus a grid of wellness cards.
- **Dashboard** — `dashboard.tsx`: a drawer-driven screen that swaps between feature sections (see below).
- **Home** — `index.tsx`: the landing page — brand header, hero card, a "what you can do" feature grid, a wellness-tip strip, a trust row, and a medical disclaimer. Feature cards link into `/dashboard`.
- **Settings** — `settings.tsx`: Profile (static), Theme (toggles light/dark via `useAppTheme()`), Language (toggles English ↔ Bangla), and **Medicine reminders** (toggles the reminder master switch; see "Medicine reminders"), plus a `__DEV__`-only "Test reminder sound" row. Every row is the same tappable value row — there is no `Switch` in this list.
- **Account** — `sign-in.tsx`: email/password + "Remember me" + "Forgot password?" (validated with `react-hook-form`). Footer links to the hidden `sign-up` route (`sign-up.tsx`, `href: null`); "Forgot password?" opens the hidden `forgot-password` route (`forgot-password.tsx`, `href: null`).

### Dashboard

`dashboard.tsx` holds an `active` section id and renders the matching component from `SECTION_COMPONENTS` (`src/components/dashboard/sections.ts`); a slide-in `Drawer` switches sections. Published sections:

- **Overview** — health-stat cards + recent activity.
- **Profile** — personal info (name, read-only email, phone, gender, blood group, date of birth) and change password. No profile image: it was removed deliberately, so don't reintroduce an avatar or an image picker. Gender and blood group are chip rows, date of birth is a `DateField` with `maximumDate` set to today; saving goes to the backend via `PATCH /auth/me`, with a cleared chip sent as `""` rather than dropped, since the server reads an absent key as "leave this alone". Email is shown `editable={false}` because it identifies the account — changing it needs re-verification and is a separate feature. **Update password** posts to `/auth/change-password` (which demands the current password even though the user is signed in) and then clears its fields and signs out to `/sign-in` behind a non-cancelable alert: that call revokes every refresh token server-side, so the session can no longer be renewed and dismissing the alert would strand the user on it.
- **Add Medicine** — a two-mode screen. A segmented control switches between **Add manually** and **Upload prescription**; upload is not a section of its own because it is the same job by another route. The manual form is name + dosage, then **When to take** (Before meal / After meal chips, optional and tap-to-clear), then **Doctor name** and **Specialty** (both optional — an over-the-counter medicine has no prescriber), then the schedule controls: **Reminder times** (preset chips Morning 08:00 / Afternoon 12:00 / Evening 18:00 / Night 22:00 toggled on and off, plus a free-form box for any other time), **Days** (seven weekday chips, all on by default), **Started on** and **End date** (both calendar pickers — see `DateField`; the end date is clearable, and blank means "Ongoing"). Below the form, two matrices read back the schedule: `MedicineWeekTable` (days of the week, with the start and end dates per row) and `MedicineScheduleTable` (clock times). Both read `useAppData()`. The prescription side (`UploadPrescription.tsx`) takes up to five photos at once and shows them as a grid of previews drawn from each image's thumbnail — held as `OptimizedImage`, never the picker's URIs, so the grid is not decoding five full-size photos. One unreadable file is counted and reported rather than thrown, so it cannot lose the other four; reading the images into a medicine is still stubbed (see `lib/prescription.ts`).
- **Medicine History** — every medicine ever added, newest first, with a per-row status badge ("Ongoing", or "Ended <date>" once `endedOn` is in the past). Each card summarises the schedule and adds the meal timing only when one was recorded. A segmented control switches between **Newest first** and **By doctor**, which regroups the same records under `doctorName` (named doctors alphabetically, with the blank-`doctorName` bucket last as "No doctor recorded"). Reading order in that mode matches how people actually search: they remember the doctor long after the date.
- **Family Member Status** — the family member list + add form, plus the **Family ID** connect card; all backed by `useAppData()`. While linked it swaps to a "Managing <name>" banner with a Disconnect button, and the add form writes to that account instead of this device.
- **Reports** — upload a lab result, scan or prescription, and browse the ones already uploaded. A title, a category chip row (Lab report / Prescription / X-ray / Other), a `DateField` capped at today, and a file — a photo from the library or a PDF from the document picker. Below the form, **Previous reports** is read from the server every time the section opens, newest first, each row offering View and Delete and showing the document's own preview where one exists, falling back to its category icon. A guest gets the same form, but the file is copied into the app's own storage and the record kept on the device — see "Guest reports" below. This is the only section that talks to the server directly rather than through `useAppData()` alone — a guest's rows, and any rows a failed sign-in flush left behind, still come from context.

**Find Doctor, Find Pharmacy, Find Hospital, and Appointments are intentionally not published in this release.** Their section components and mock data remain in `src/components/dashboard/sections/` and `src/components/dashboard/mock.ts` so they can be re-enabled later — just re-add them to `sections.ts` and to the `SectionId` union in `src/components/dashboard/types.ts`.

### The medicine schedule model

A `Medicine` is `{ id, name, dosage, times, days, startedOn, endedOn, doctorName, specialty, mealTiming }` — two **independent** schedule axes, a date range, who prescribed it, and when to take it:

- `times` — sorted unique 24h `"HH:mm"` strings. **Frequency is not stored**; it is derived as `times.length` and shown as `2×/day`, so a medicine can never claim a dose count its own schedule contradicts. There is no per-slot tablet count; a time is simply on or off.
- `days` — sorted weekdays taken, as `Date.getDay()` values (0=Sun..6=Sat), so they stay meaningful against a real date. A day left out is a day it is *not* taken; `ALL_DAYS` means daily.
- `startedOn` / `endedOn` — local `"YYYY-MM-DD"` strings, not timestamps: they are calendar dates, so an instant type would drag timezone conversion into a value that has none. **`endedOn: ""` means the course is ongoing** — the normal case for a chronic medicine, so it is a real state rather than a missing value.
- `doctorName` / `specialty` — who prescribed it, and their field. Both are **optional by nature** (`""` = not recorded), because plenty of medicines are bought over the counter, and a required doctor would make those impossible to record. Nothing is derived from them; they exist so Medicine History can group by prescriber.
- `mealTiming` — `"before" | "after" | ""`, i.e. before or after food. Optional for exactly the same reason: many medicines have no meal relation at all, so `""` is a real answer and not a gap. The two options live in `MEAL_TIMINGS` (`src/lib/medicineSchedule.ts`) and the server accepts nothing else, so widening the set is a code change on both sides and never a migration.

The two tables show the cross-product: `MedicineWeekTable` (columns from `WEEK_DAYS`, Sat-first to match the Bangladeshi calendar, plus each row's start/end dates) and `MedicineScheduleTable` (columns from `unionTimes`).

`src/lib/medicineSchedule.ts` owns the shared logic — `TIME_PRESETS`, `WEEK_DAYS`/`ALL_DAYS`, `MEAL_TIMINGS`, `parseTime` (tolerant input: `8`, `8:30`, `0830`, `8pm`, `20:00`; rejects anything ambiguous or out of range), `todayISO`, `isValidDateString`, `isoDate`/`parseISODate`/`formatDate`, `sortTimes`/`sortDays`, `presetLabel`/`dayLabel`/`mealTimingLabel`, the defensive readers `timesOf`/`daysOf`/`startedOnOf`/`endedOnOf`/`mealTimingOf`, `unionTimes`, `frequencyLabel`/`daysLabel`, `recoverFromLocal`. Prefer these over re-deriving the same rules in a component.

**Dates are picked, not typed.** `src/components/ui/DateField.tsx` wraps `@react-native-community/datetimepicker`: Android uses the library's imperative `DateTimePickerAndroid.open` (its picker *is* a dialog, so there is no component to mount and no `visible` state to fall out of sync), and iOS renders the inline calendar inside a `Modal` we control. It uses `onValueChange`/`onDismiss` — `onChange` still works but logs a deprecation warning. Reach for `DateField` rather than a `TextInput` for any new date.

**Records predating this model are migrated on read, not dropped.** AsyncStorage holds whatever an older build wrote, so `loadMedicines` runs every record through `normalizeMedicine`, which adopts any clock times it finds in the legacy `time` string (`"08:00, 20:00"`) as the new schedule, tolerates a missing/`undefined` `times`, and fills `days`/`startedOn`/`endedOn` with their defaults when absent or malformed. A record with no usable weekdays gets `ALL_DAYS` rather than an empty list — "no days" would mean a medicine that is never taken, which the form refuses to create and the server rejects, so one such record would fail an entire sync payload. An `endedOn` before its `startedOn` is likewise treated as ongoing: the form cannot produce it, and rendering "Ends Oct 1" under "Started Oct 7" would be worse than showing nothing.

The sync merge is add-only, so `recoverFromLocal` also refills a medicine the server holds with an **empty `times`, blank `startedOn`, or blank `endedOn`** from the device copy — without it, signing in would erase a schedule that only the device still remembers. `days` is deliberately *not* recovered: its blank state already means the all-7 default. `doctorName` / `specialty` are not recovered either, for a different reason: no medicine already on the server can have had a prescriber, since the columns did not exist when those rows were written and there is no edit path to add one. `mealTiming` is in that same group — a server row with a NULL timing predates the column, so the device copy is blank too and there is nothing to refill it from. The recovery is device-local: the server copy stays empty until medicines get an update path.

### Medicine reminders

`src/lib/notifications.ts` turns a medicine's schedule into **local** notifications — no server, no push tokens. The reason is structural rather than a shortcut: a reminder's whole content (which medicine, what dose, at what time) is already on the device, and local notifications fire offline and survive the app being killed, which is the only way a reminder can be trusted. Title is the medicine's name and the body is the dosage plus "· before/after food", so the notification itself says what to take rather than sending the user into the app to find out.

**The unit of work is reconciliation, not scheduling.** `syncMedicineReminders(medicines, enabled)` derives the desired set, diffs it against `getAllScheduledNotificationsAsync()` by identifier, cancels what is no longer wanted and schedules what is missing — which is what stops a finished course from ringing forever, and what repairs the queue after a reinstall. It runs from an effect in `AppDataContext` keyed on `hydrated`, `medicines` and `notificationsEnabled`. Identifiers all carry the `reminder:med:` prefix, the only thing that distinguishes our notifications from anything else in the OS queue; `isMedicineReminder` is that test, and the tap handler in `src/app/_layout.tsx` routes a tap on one to `/dashboard`. It reads the list back from **storage** rather than using `medicines` from context, because while a family member is linked the on-screen list is *theirs* — ringing here for a relative's dose would be wrong. Reminders are therefore always this device's own medicines, for guests and signed-in users alike. The helper never throws: a scheduling failure must not disturb the medicine list it was derived from, and the next run reconciles whatever was missed.

**A daily medicine collapses to one repeating trigger per time**, not seven, because iOS caps an app at 64 pending notifications and a sevenfold inflation would reach that with a handful of medicines. Android takes `daily`/`weekly` triggers, iOS has neither and reaches both through a repeating `CALENDAR` trigger on its `hour`/`minute`/`weekday` components. Both platforms number weekdays **from 1 with Sunday first**, so a stored `Date.getDay()` value is shifted by one in `weeklyTrigger` — get that wrong and every reminder is silently a day off.

**The master switch is `notificationsEnabled`** (`ownmed.notificationsEnabled`, default **on**; only an explicit `false` turns it off, so devices that never wrote the key keep behaving as before). It is a device preference, not an account one — it governs what this phone rings for. It is applied by emptying the desired set rather than by returning early, so "off" cancels through the same diff that retires a finished course; one code path, and off cannot leave a stale reminder behind. The notification permission is requested **only when the desired set is non-empty**, so a fresh install with no medicines is never prompted.

**The bell in `DashboardHeader` is a schedule, not a history.** It lists today's doses via `todayDoses(medicines)` — active course, today's weekday, every time, sorted across all medicines so it reads as a day's plan — which is deterministic and identical on any device, where a record of delivered notifications is not: the OS keeps nothing readable once the app is killed, and iOS's pending queue is capped. It reads from storage on open, for the same reason the sync does, and shows a "reminders are off" note when the switch is down so a silent day is not mistaken for a bug.

**The sound is a bundled file, `assets/reminder.wav`**, registered through the `expo-notifications` plugin's `sounds` option: the plugin copies it to `res/raw/reminder.wav` on Android and adds it as an Xcode resource on iOS, and both platforms then refer to it by that bare filename (`REMINDER_SOUND`) — Android resolves it through `SoundResolver`, which strips the extension and looks the basename up in `raw/`. Android 8+ takes the sound from the **channel**, so that is where it is set (`ensureChannel`); iOS reads it off the notification's `content`. The shipped clip is a generated placeholder chime — **a real recording replaces it at the same path, and needs no code change**. A spoken reminder can only ever be a static clip: the OS cannot synthesise speech while the app is killed, and one clip cannot name each medicine, which is why the medicine's name travels as notification text instead.

The channel is created at runtime rather than via the plugin's `defaultChannel`, deliberately: the plugin would pre-create it and **Android locks a channel's importance once created**, so the runtime `AndroidImportance.HIGH` could never be applied afterwards. The plugin's `icon` is likewise omitted, since Android masks notification icons by alpha and a wrong guess renders a solid white blob.

**Settings carries a `__DEV__`-only "Test reminder sound" row** (`scheduleTestReminder`), because a real dose is a repeating trigger at a time of day and checking a new clip would otherwise mean waiting for that clock time. It schedules the *same* notification the sync would — same channel, same `REMINDER_SOUND`, same content shape — five seconds out via a one-shot `timeInterval` trigger, so a test cannot pass on a code path the real reminders do not take. Its identifier deliberately lacks the `reminder:med:` prefix, or reconciliation would cancel it as unwanted on the next sync, quite possibly before it fired. It returns a result object rather than throwing, unlike the rest of the file, because reporting failure *is* its job; the row is gated on `__DEV__` (confirmed absent from a production bundle) but **not** on `remindersSupported()`, since the state most worth poking at is the one where reminders cannot load at all. Two caveats it cannot route around: a channel that already has its sound pinned will play the old clip and still report success, and a notification arriving while the app is open goes through the foreground handler — leaving the app is what exercises the real delivery path.

`expo-notifications` is a **native** module, and `app.json` carries its plugin — an existing dev client will not have it (nor `expo-image-manipulator`, from the image work) until the next native build.

**Never `import` `expo-notifications` — load it through `loadNotificationsApi`.** Importing that package is not a neutral act: its `index.js` re-exports `DevicePushTokenAutoRegistration.fx`, whose module scope registers a push-token listener, which calls a guard that deliberately **throws on Android in Expo Go** ("remote notifications were removed from Expo Go with the release of SDK 53"). So a static import anywhere reachable from the root layout kills the whole app at launch, in the one environment most likely to be used for development — and the stack trace points at the import line, which makes it look like a local mistake. `src/lib/notifications.ts` therefore imports it **type-only** and pulls the real module in through `require` behind two checks (not web, not Expo Go on Android) inside a `try/catch`; everything else in the file reads the resulting `api`, which is `null` where the module cannot load. iOS Expo Go *can* serve reminders — the package only warns there — so the guard is about one platform, not about Expo Go as a whole. The consequence is a deliberate degradation to the same "no reminders" state as a denied permission: the app is unaffected and the bell still lists the schedule, and `remindersSupported()` is what lets Settings say "Unavailable" instead of offering a switch with nothing behind it. Note the two knock-on rules this creates: the trigger kinds are reached via `triggerKinds` (a bare `"calendar"` is *not* assignable to the SDK's string enum), and the tap listener is wrapped by `addReminderTapListener` so `src/app/_layout.tsx` never touches the package either.

### State & persistence

- `src/lib/storage.ts` — typed AsyncStorage wrapper. Keys are namespaced (`ownmed.*`). The `onboarded` key is versioned (`.v2`) so bumping it re-shows the walkthrough. Holds `authUser` + `authTokens`, the health profile, the medicine / family-member lists, `familyLink`, the guest report list (`localReports`), and the reminder preference (`notificationsEnabled`; see "Medicine reminders").
- `src/lib/api.ts` — typed `fetch` client (`register`, `login`, `requestPasswordReset`, `confirmPasswordReset`, `logout`, `updateProfile`, `changePassword`, `getSync`, `postSync`, `connectFamily`, `getFamily`, `postFamily`, `getReportUploadUrl`, `createReport`, `listReports`, `getReportDownloadUrl`, `getReportThumbnailUrls`, `deleteReport`). The base URL is `EXPO_PUBLIC_API_URL` when set — a built app has no Metro host to infer from, and Expo inlines `EXPO_PUBLIC_*` at build time — otherwise auto-detected from Expo's `hostUri` (LAN IP), with a null override for manual config. It also owns the session tokens; see "Token lifecycle".
- `src/lib/prescription.ts` — the seam where prescription reading will land. `parsePrescription()` currently throws; it is the single place a vision provider gets wired in, so nothing else has to change when it becomes real.
- `src/lib/reports.ts` — everything device-side about a report file: `REPORT_CATEGORIES` (+ `categoryLabel`), the two pickers behind `pickReportFile` and the asset-level `pickedFileFromAsset` (shared with the prescription uploader, which picks several images at once), the `mimeType`/size normalization (`normalizeMimeType`, `resolveSize`, `MAX_REPORT_BYTES`), the upload (`uploadReportFiles`, which PUTs the preview behind the file), `isImageReport`, `formatFileSize`, `reportErrorMessage`, and the guest half — `persistReportFile` / `persistThumbnailFile` / `deleteReportFile`, which copy a picked file into the app's document directory and remove it again (the copy is **verified** before its URI is returned, so a record is never written for bytes that did not arrive). `localFileExists` backs the "file is not on this device" case, and `openLocalFile` is the `expo-sharing` call that opens a local PDF. It holds no *records*; a guest's report rows live in `lib/storage.ts` under `ownmed.localReports`. See "Reports".
- `src/lib/imageOptimization.ts` — the resize/compress/preview pass every picked image goes through before it is uploaded (`optimizeImage`, `MAX_IMAGE_EDGE`, `THUMBNAIL_EDGE`, `UPLOAD_JPEG_QUALITY`, `OptimizedImage`). It is the reason the pickers ask for `quality: 1`, and the only place a `ReportPickError` for an overweight image is raised. See "Image optimization & previews".
- `src/context/AppDataContext.tsx` — `AppDataProvider` + `useAppData()` exposing `hydrated`, `onboarded`, `healthProfile`, `authUser`, `medicines`, `familyMembers`, `familyLink`, `syncPending`, `localReports`, and actions `completeOnboarding`, `skipOnboarding`, `addMedicine`, `addFamilyMember`, `addLocalReport`, `deleteLocalReport`, `lookupFamily`, `connectFamily`, `disconnectFamily`, `updateProfile`, `changePassword`, `register`, `signIn` (takes a `rememberMe` flag), `requestPasswordReset`, `confirmPasswordReset`, `signOut`. Wraps the whole app in `src/app/_layout.tsx`.

- **Guest vs. registered.** Everything is written to AsyncStorage first, for guests and signed-in users alike, so the UI reads local data and works offline. Registering/signing in persists the returned `authUser` + tokens locally — but only when "Remember me" is checked; otherwise the session is in memory and lost on restart.

`medicines` / `familyMembers` are the **active scope**, not necessarily the user's own — see "Family ID" below.

### Guest mode & sync

New records get a **client-generated UUID** (`expo-crypto`'s `randomUUID()`), assigned before the row ever reaches the server so the sync upserts stay idempotent.

`register` and `signIn` both end with `syncWithAccount()`, which `POST`s the whole local snapshot to `/sync` and **adopts the merged result** as the new local state — and then with `flushPendingReports()`, which uploads whatever a guest added to *this device* (currently the local reports; see "Guest reports"). The two are separate calls in that order because they answer to different rules: `/sync` is a merge of records the server already models, while a report is a file that has to be PUT to storage before a row can point at it. The merge is add-only: medicines and family members upsert by id (`ON CONFLICT DO NOTHING`), and the health profile is written only when the account has none — so a returning account is never overwritten by whatever an anonymous device happened to hold.

**A signed-in add does not wait for the next sign-in.** `addMedicine` also pushes just that one medicine to `POST /sync` immediately (`pushOwnMedicine`), best-effort and *without* adopting the response: the optimistic list is already correct on screen, while the server's snapshot would omit any other local row that has not been pushed yet. It goes through the ordinary authenticated call, so it reaches the server for a "remember me"-less session too — the token lives in `lib/api` for the life of the session either way, which is also why `updateProfile` needs no special handling. Only a guest stays local, and is carried up by the next sign-in; nothing is lost, only deferred. `addFamilyMember` does **not** push yet and still relies on the sign-in sync.

The sync is deliberately best-effort: a failure never blocks signing in. It sets a persisted `syncPending` flag instead, and the next sign-in retries. **Nothing retries while the app is closed** — there is no background task, so signing out and back in is what clears a failed sync.

**Guest Data Policy.** Guest data is device-local and gone on uninstall — the uploaded documents a guest adds included, which is why the Reports section carries its own note saying so where the files are actually added. `src/components/ui/GuestBackupBanner.tsx` (rendered at the top of the dashboard) carries the standing prompt to create an account; sign-out deliberately **keeps** local data rather than wiping it, since that cache may hold records that never reached the server.

Auth: **Sign In / Sign Up are wired to the backend** (`sign-in.tsx` and `sign-up.tsx` call `signIn`/`register` from `lib/api.ts`, then `router.replace('/dashboard')`). `signIn` takes a `rememberMe` flag — unchecked (default) keeps the session in memory only, checked persists it to AsyncStorage. **Forgot password** (`forgot-password.tsx`) sends a Resend-emailed 6-digit code via `/auth/password-reset/*`. **Sign out** (the avatar menu in `DashboardHeader`) revokes the refresh token via `/auth/logout` and returns to `/sign-in`. Google sign-in has been removed and will be re-implemented later.

`DashboardHeader`'s avatar is the user's **initials** (`initialsOf` — first and last word, so "Rahim Uddin" is "RU"), not an icon or a photo; the same dropdown below it shows the Family ID when signed in, or a "sign in to get one" hint for guests.

The onboarding `healthProfile` feeds **Dashboard → Overview**: weight and blood pressure are overridden when present; other stats fall back to `HEALTH_SUMMARY` mock values.

### Token lifecycle

The token pair lives at **module scope in `src/lib/api.ts`**, not in React state — a retried request has to swap it *inside* a call, outside any render, at a moment when no component is mounted. `AppDataContext` mirrors it into state and (for a "remember me" session) onto disk, and registers two listeners, but `lib/api` is what a request actually consults.

An authenticated call that comes back **401 refreshes once and retries**; a second 401 is surfaced as-is, since a token minted moments ago being refused is not a freshness problem. Two mechanisms carry the weight:

- **Single-flight.** Refresh tokens are single-use — the server deletes the row on rotation and refuses reuse — so several screens 401-ing at once must share **one** refresh. Concurrent refreshes would race, and every loser would look like a stolen token. All callers await one module-level promise.
- **A generation counter.** A refresh that started before a sign-out must not land afterwards and resurrect the session, so it captures the counter and discards its result if the counter has moved.

**Only a 401/403 ends the session** — an explicit refusal of the token itself. A network failure or a 5xx is the server having a bad moment, so the tokens are kept and the error surfaces with the server's status (or `statusCode 0` for an unreachable host); signing the user out there would turn a blip into a forced re-login. When the session *is* over, `onEnded` clears the tokens and routes to `/sign-in`, rather than leaving the user on a dashboard that has silently become the guest view.

`signOut` revokes the **live** refresh token rather than the one on disk: after a refresh those differ, and revoking the stale copy would leave the real session alive on the server.

### Family ID

Every account gets an 8-character **Family ID** (`users.share_id`, shown in the dashboard header dropdown and copyable there). A relative types that code into **Dashboard → Family Member Status → Connect** and can then add medicines and family members to that account — **without signing in**. That is the point of the feature, so the connect card is deliberately available to guests; don't gate it behind auth.

The code resolves in two steps so a typo costs nothing: `lookupFamily(shareId)` resolves it to a name and throws if unknown, the UI asks "Connect to <name>?", and only then does `connectFamily(contact)` change scope. `disconnectFamily()` clears the link and reloads **this device's own** lists from AsyncStorage.

What "scope" means in practice:

- `medicines` / `familyMembers` in `useAppData()` are whatever is currently being managed, which is the linked member's data while `familyLink` is set. **Add Medicine, Medicine History and Family Member Status all follow it for free**, because they read those lists rather than fetching their own. **Reports deliberately do not** — a Family ID grants access to medicines and family members, not to someone's lab results, so the section ignores `familyLink` entirely and always shows the signed-in user's own account.
- `addMedicine` / `addFamilyMember` **branch on `familyLink`**: linked writes go to the family account via `POST /family/:shareId` and are *not* written to this device's cache — a family member's medicine saved locally would reappear in the user's own list the moment the link dropped.
- `familyLink` persists (`ownmed.familyLink`), and an effect keyed on `linkedShareId` refetches on restart, since hydration can only load the *device's* own lists from disk.
- Signing in while linked pushes **the device's own** lists (`loadMedicines()`/`loadFamilyMembers()`), never the ones on screen — otherwise a family member's records would be silently copied into the account. The same reason makes `applyServerState` take an `adoptDomain` flag: the account's data is still written to the cache, but the on-screen lists are left alone while linked.

**The Family ID is a bearer credential.** Whoever knows the 8 characters gets read + append access to that account's medicines and family members; the routes are unauthenticated by design. Three things bound the damage: the server merge is add-only (no update, no delete, so the worst case is spurious rows), an id already owned by a third account is skipped rather than reassigned, and the account owner's `health_profiles` row is excluded from every `/family/*` response. `POST /family/connect` is rate-limited server-side (which throttles guessing, not the design); if this is ever revisited further, the direction is invite/accept with signed tokens — **not** bolting `authenticate` onto the routes, which would break the guest flow the feature exists for.

### Reports

An uploaded report is the **one resource that is not purely local-first** for a signed-in user, and every design choice here follows from that. The bytes are in object storage, the row is on the server, and the list is fetched when the section opens. Offline, the list is simply unavailable — there is nothing cached to show, and a stale copy of someone's lab results is worse than an empty state. A guest has no account for a report to belong to and no session to sign an upload with, so their reports stay on the device rather than being refused; see "Guest reports" below.

A server `Report` is `{ id, title, category, takenOn, file: { storageKey, fileName, mimeType, sizeBytes, thumbnailKey } }`. `storageKey` names the object; there is deliberately no local URI, because nothing about a server report is viewable without a round trip. `thumbnailKey` is `""` when the report has no preview — a PDF, or a row written before previews existed.

**The upload is three calls, in an order that matters** (`Reports.tsx` → `onSubmit`):

1. The client mints the UUID first, then `api.getReportUploadUrl({ id, ... })` reserves the object key and returns a presigned PUT.
2. `uploadReportFile(uploadUrl, file)` sends the bytes **directly to storage** — they never touch the API.
3. `api.createReport(...)` records the row.

Minting the id up front is what lets the key and the row share it, so a retry overwrites the same object rather than orphaning the first. Uploading before recording is what guarantees no row ever points at an object that was not written. And the list is re-read from the server after a write rather than patched locally, so what is on screen is what was actually stored.

**`mimeType` is normalized before it is sent, and that is load-bearing.** The value is signed into the upload URL, so storage rejects the PUT if the `Content-Type` header differs from what was signed — both the reservation and the upload must therefore use the same normalized value. `normalizeMimeType` maps the non-standard `image/jpg` that some Android cameras report onto `image/jpeg`, falls back to the file extension, and only then to a default. The pickers are asked for a size too, but Android's photo picker often omits it, so `resolveSize` reads it off the file itself — `0` means "could not be determined" and the server accepts that rather than rejecting the upload over metadata the user cannot influence.

`launchImageLibraryAsync` is called with `preferredAssetRepresentationMode: Compatible` so iOS transcodes an iPhone's HEIC to JPEG at pick time. A report is uploaded on one device and read later on whatever the user has then, and Android does not decode HEIC — without this, a photo attached on an iPhone could come back as a broken image. iOS-only; Android needs no equivalent.

`uploadReportFile` checks `result.status` itself: an Expo upload task resolves for *any* completed HTTP response, including a 4xx, so without that check a failed upload would look like a success and the report would be created pointing at an object that was never written. A 403 is reported as an expired link, because that is what it almost always is — storage has no idea who is calling.

#### Image optimization & previews

Every image is **resized and re-encoded on the device before it is uploaded** (`src/lib/imageOptimization.ts`, `optimizeImage`). That is the only place the work can happen: the bytes go device-to-storage through a presigned URL and never pass through the API, so the server never gets a chance to shrink anything — an oversized photo would either be refused by the size cap or stored at camera resolution forever. Both pickers hand their assets straight to `optimizeImage`, which is why they ask for `quality: 1`: a picker that had already discarded quality would leave it nothing to work with.

The target is set by **legibility rather than by size** — `MAX_IMAGE_EDGE` is 2048 px and `UPLOAD_JPEG_QUALITY` 0.85, roughly twice what a 3× screen resolves when a page is shown whole and still enough to zoom into a printed lab value. An image larger than the cap is scaled to fit it; one already within it keeps its own dimensions but is **still re-encoded**, because the copy in storage is the copy someone will actually read, not the one a sensor wrote. Nothing is ever upscaled. If one pass still leaves it over `MAX_REPORT_BYTES`, a single harder squeeze is tried and then it is refused *with the file's own size* — a loop would only be a slower way to say no. That refusal is a `ReportPickError`, so the form can report the weight instead of failing later on the server.

Re-encoding always produces **JPEG**, including from a PNG, and that is a deliberate trade: PNG is lossless, so re-encoding it at any quality would leave the size essentially unchanged and fail at the thing it was called to do. The name follows the bytes (`renameForJpeg`) — a stored name ending in `.heic` would describe something that is no longer there. The one exception runs a single way: an image the device **cannot** re-encode at all comes back as it was picked when it is already within the cap, since compression is the goal and not the price of admission; over the cap there is no such choice, because the server would reject it and the failure has to be shown. A PDF comes straight back untouched, which is what lets the callers not branch on the kind of file they picked.

A **thumbnail** (`THUMBNAIL_EDGE`, 512 px) is a separate, small copy made for lists — never a downgrade of the stored file. It is best-effort by contract: null for a PDF and for an image whose dimensions could not be read, and a null preview fails nothing, because a preview resized against a guessed dimension is how an image ends up squashed. Dimensions themselves are read with `renderAsync` alone, which costs a decode but **no re-encode**, so measuring an image can never be the thing that degrades it.

Previews are what make the list readable rather than a column of identical document icons, and the prescription grid draws the same thumbnail instead of decoding five full-size photos — the difference between a grid that scrolls and one that stutters on a mid-range Android. A preview travels as its own object: the server signs a second key when the upload is reserved, the device PUTs it *behind* the file (`uploadReportFiles`, in that order and idempotent about the preview — a report that uploaded cleanly must not be reported as failed because its preview did not), and the row carries `thumbnailKey`. A preview is not signed for a PDF, because there are no pixels to sign for and the extra URL would only be a second way for the upload to half-fail. Previews are read through their own endpoint and their own call (`getReportThumbnailUrls`) rather than as a field on the list, because the URLs expire and embedding them would take the list stale with them; a failure there means "show the category icons" and nothing more. A guest's preview is copied in beside the document by `persistThumbnailFile`, named after the report's id like the document itself, so deleting the report finds both by id alone.

**Viewing is two paths, and a PDF splits them again by where its bytes are.** Images open in-app in `ReportViewer` (a full-screen `Modal` with `resizeMode="contain"` — a lab report is read, so cropping it would hide the part that matters), from a local `file://` URI or a signed URL. A **server** PDF is a plain https URL, so `Linking.openURL` hands it to the browser: no PDF renderer exists in this app, and the browser is a better one than anything a screen here would do.

A **local** PDF cannot go that way, and the reason is worth keeping: React Native's `openURL` builds a bare `ACTION_VIEW` with **no MIME type and no `FLAG_GRANT_READ_URI_PERMISSION`**, so a `content://` URI handed over that way is one the receiving app is not permitted to read — and on iOS a `file://` URI is unreadable by every other app by design. `expo-sharing`'s `shareAsync` sets both and is the only path that works on either platform; `openLocalFile` (`lib/reports.ts`) is that call, and the share sheet is the point rather than a compromise, since an Android chooser can offer Files or Drive where nothing has registered as a PDF handler at all. **Do not "simplify" this back to `Linking.openURL` with `File.contentUri`.**

A server report needs a *fresh* presigned URL for either viewer, which is why View is a round trip with a spinner rather than a tap-through; a local one needs nothing signed and nothing fetched. `react-native-pdf` is the upgrade path if in-app PDF rendering is ever wanted.

Delete exists **only** for reports. Medicines and family members are append-only by design; a document uploaded by mistake is not the same kind of record as a dose that was taken.

Reports are **per-account**: not part of `/sync`, not reachable by Family ID, and a family link never redirects them — the guest flush writes only to the account that signed in, which is why the section ignores `familyLink` entirely. The *server* list is gated on `authUser`, and on `hydrated` so the moment before `authUser` comes back from disk doesn't read as "guest". A guest keeps the form either way.

#### Guest reports

A guest can add a report; it just cannot leave the device. `LocalReport` (`src/components/dashboard/types.ts`) is the device-side shape — `{ id, title, category, takenOn, file: { uri, fileName, mimeType, sizeBytes, thumbnailUri } }` — where `file.uri` is a `file://` path in the app's document directory and `thumbnailUri` is `""` when no preview was made. The picked file is **copied** there by `persistReportFile` rather than referenced where the picker left it, because that is a cache directory (or, on Android, a `content://` reference into another app's sandbox) and neither is a place a report can live for months. `Paths.document` is the directory Expo documents as safe from being deleted by the system — exactly the lifetime this needs: as long as the app is installed, and gone with it. The copy is named after the report's id so two reports made from the same photo cannot collide; the name the user sees stays in `fileName`.

`lib/storage.ts` owns the rows under `ownmed.localReports` (`loadLocalReports` / `saveLocalReports`), with a `normalizeLocalReport` that drops any record with no id **or no `file.uri`** — a report whose bytes cannot be found is not a report, and every row renders an open button, so it would otherwise fail only when the user tapped it. `AppDataContext` owns the list and exposes `localReports`, `addLocalReport`, `deleteLocalReport`; `addLocalReport` returns a promise (unlike `addMedicine`) so a failed copy — a full disk — surfaces through the same `reportErrorMessage` path as a failed upload.

**Signing in is what carries them up.** `register` and `signIn` call `flushPendingReports()` after `syncWithAccount()`: each local report runs through the same three calls the signed-in form uses, and on success its record is dropped and its file deleted. It is best-effort and *per report* — a failure keeps that record and moves on to the next — so signing in can never lose one, only defer it.

`Reports.tsx` renders both kinds from one flattened `ReportRow` (`local: boolean`), so the row, its View/Delete buttons and the empty state are written once and cannot drift between the two paths. Only three places branch: the submit (`addLocalReport` vs the three-call upload), `onOpen`, and `onDelete`. A signed-in user with leftovers from a failed flush sees those rows above the account's under a count; a guest sees the same rows under a note that they are on this device only and that creating an account copies them up.

Four **native** modules back this section — `expo-file-system` (the upload task, reading a file's size, and the guest's local copy), `expo-document-picker` (the PDF picker), `expo-sharing` (opening a local PDF in another app) and `expo-image-manipulator` (the resize/compress/thumbnail pass; see "Image optimization & previews"). None of them *needs* a config plugin, but an existing dev client won't have them until the next native build. Note that `npx expo install expo-sharing` appends an `expo-sharing` entry to `app.json`'s plugin list on its own: that plugin configures *receiving* shares, which this app does not do, so it was removed — leave it out if a reinstall adds it back. Note also that `expo-image-picker` is configured in `app.json` with real `photosPermission`/`cameraPermission` copy: those strings are what the OS dialog displays, and the Reports flow is what surfaces the photo one — leave them meaningful rather than reverting them to placeholders.

### Backend

The API lives in **`ownMed_server/`** — a separate npm project (Express 5 + TypeScript + Neon PostgreSQL) with its own `AGENTS.md`. Auth is live (`/auth/register`, `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/me`, `PATCH /auth/me`, `/auth/change-password`, `/auth/password-reset/*`), and `src/lib/api.ts` calls all of it — `/auth/refresh` included, which is what "Token lifecycle" above is about. Guest-to-account sync is live at `GET`/`POST /sync`. The family share routes are live at `/family/connect`, `GET`/`POST /family/:shareId` and are **unauthenticated** (see "Family ID"). Reports are live at `/reports` — authenticated, presigned upload/download against Cloudflare R2, and the only resource with a `DELETE`. Per-resource CRUD routes otherwise do not exist — sync is the only way domain data reaches the server for the account owner, and `/family/*` for a linked member.

### Theme

`src/theme/index.ts` exports `useAppTheme()` → `{ isDark, colors, toggleColorScheme }` plus the `brand`/`status` palettes in `src/theme/colors.ts`. Style with NativeWind `className` (CSS variables in `global.css`); reach for `colors`/`brand` only where a raw value is required (icons, navigation chrome).

### Fonts

**Inter** (primary) and **Manrope** (accent/headings) are loaded in `src/app/_layout.tsx` via `@expo-google-fonts/*`. RN uses a separate file per weight, so `tailwind.config.js` remaps `font-medium`/`font-semibold`/`font-bold` to the matching Inter family (they normally set `fontWeight`, which does nothing here). Use `font-sans` for regular body text and `font-display` / `font-display-bold` for Manrope headings.

### Shared components

- `src/components/ui/FormField.tsx` — labelled `TextInput` with a leading icon and shared focus/error border + icon states. Used by sign-in, sign-up, forgot-password, and the onboarding modal. Prefer it over ad-hoc text fields for new forms.
- `src/components/ui/DateField.tsx` — labelled calendar picker with the same card styling, for any date input. Prefer it over a typed date. Takes `maximumDate` / `minimumDate` to bound the range (Profile passes `maximumDate={new Date()}` for date of birth), and `clearable` where blank is a real state. Backed by `@react-native-community/datetimepicker`, a **native** module: `npx expo install` added it to `app.json`'s plugin list, and an existing dev client won't have it until the next native build.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`. Note that `npx expo install` may also append a config plugin to `app.json` on its own — check `git diff` after installing and commit that change with the dependency.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md
